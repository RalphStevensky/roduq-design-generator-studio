# Audyt ekspercki — czerwiec 2026 (Claude Fable 5)

> Pełny audyt projektu wykonany 2026-06-11 przez Claude Fable 5 na zlecenie Roduq.
> Zakres: architektura, skills, design systems, JSON Schema v1, MCP server, testing, luki implementacyjne, modernizacja, wizja innowacyjna.
> Powiązane: [REMEDIATION_PLAN.md](REMEDIATION_PLAN.md) (plan naprawczy z przypisaniem modeli), [MODEL_STRATEGY.md](MODEL_STRATEGY.md) (dobór modeli LLM), rule `010-model-strategy.mdc`.

## Executive summary

Projekt to **wybitnie udokumentowana specyfikacja udająca produkt**. Z ~22 000 linii "Roduq additions" jedyny wykonywalny kod to MCP server (~1900 LOC), który **nigdy nie został zbudowany** (brak `dist/`), a testy **nigdy nie zostały uruchomione** (`node_modules` częściowy — brak vitest, ajv, better-sqlite3). Nie istnieje żadna linia kodu generacji: brak `src/llm/`, brak skill runnera, brak formularza briefu w UI. Dokumentacja systematycznie zawyża status (odhaczone checkboxy performance, których nikt nie zmierzył; "1860 LOC" SKILL.md, który ma 204 linie). Architektura jest w większości trafna, kontrakty przemyślane — dystans do działającego v1.0 to **10-15 dni roboczych wiring'u**, nie przepisanie. Cel "<30s" jest matematycznie niemożliwy przy zadeklarowanym wolumenie outputu (8-15k tokenów outputu per wariant ≈ 100-250 s per call).

## Część I — Ocena jakości (werdykty)

### A) Architektura

1. **Skills = markdown** — trafna konwencja (zgodna z upstream, edytowalna, wersjonowana), ale **maskuje brak runtime'u**: nie istnieje maszynowy kontrakt egzekutora (kto składa prompt, w jakiej kolejności, z jakimi parametrami). Fix: manifest egzekucji we frontmatter (`inputs`, `outputs`, `prompt_assembly`, `llm`).
2. **Standalone package MCP** — dobry wybór (cherry-pick safety, licencje), ale Tool 2 wylądował w złej warstwie (wymaga LLM = kompetencja daemona). Fix: `packages/roduq-output-protocol` współdzielony + Tool 2 jako cienki klient HTTP daemona.
3. **File protocol** — przemyślane podstawy, naiwne krawędzie: sprzeczność `.complete` (F-05), Windows rename nieatomowy, brak locka współbieżności, brak manifestu integralności. Fix: `.complete` z treścią `{generationId, manifest: {plik: sha256}}`; CLI nie usuwa flagi, zapisuje skonsumowane ID lokalnie.
4. **Macierz 7×3** — sensowna konstrukcja, ale `roduq-default` obsadza Conservative w 4/7 branż (najczęściej wybierany wariant = generyczny). Braki branż chleba polskiej agencji: e-commerce, beauty, kancelarie/biura rachunkowe, budowlanka, hotel/pensjonat, edukacja, eventy. Plus sprzeczność F-07.
5. **Multi-provider LLM** — **czysto zadeklarowana** (F-01). Rekomendacja: Mock + Anthropic najpierw, OpenAI/Gemini dopiero na żądanie klienta (YAGNI); interfejs abstrakcyjny wystarcza jako gwarancja braku lock-inu.

### B) Skills

6. **saas-landing SKILL.md** — dobra struktura 8 kroków i zasady voice; luki: F-08, F-09, brak ani jednego kompletnego przykładu outputu JSON (fixtures `schemas/examples/` istnieją i **nie są linkowane** — najtańsza poprawa jakości), brak limitów długości copy, brak instrukcji formatu odpowiedzi.
7. **Non-determinizm** — wysoki; brak: golden examples, structured output enforcement (tool-use/JSON schema w wywołaniu API — patrz MODEL_STRATEGY.md), parametrów per krok, checklisty samoweryfikacji.
8. **7 głosów** — tabela honoryfikatyw (clinic "Pan/Pani", saas "Ty") to autentyczna polska wartość, ale ~70% treści skills to powielony boilerplate. Rekomendacja: hybryda — jeden `roduq-page-generator` + 7 lekkich industry packs.
9. **Conservative/Modern/Bold** — framing risk-curve dojrzały; Bold=brutalist to spalony slot dla większości MŚP — rozważyć trzeci kierunek "Elegancki/Premium-tradycyjny" dla segmentów konserwatywnych. Walidować danymi (design memory).

### C) Design systems

10. **Jakość presetów** — "wystarczające", nigdzie "wybitne". Mocne: dual-layer tokens.css (white-mix hover, oklch, barwione cienie). Braki do poziomu Linear/Stripe: specyfikacja komponentów (button states), rytm spacingu, art direction fotografii, motion choreography. DESIGN.md ~70 linii to za mało, by LLM nie wypełniał luk losowo.
11. **Pokrycie rynku** — braki: klasyczny corporate-trust (granat+serif — kancelarie/finanse), e-commerce product-grid, playful/family. Nakładanie: soft-pastel vs monolith-meadow. Brutalist ~nigdy komercyjnie w tym segmencie.
12. **Dual-layer tokens** — rozwiązuje realny problem kosztem 3 słowników bez generatora. Fix: tokens.json jako source of truth + codegen → tokens.css.
13. **Lint compliance** — warstwa 1 tak; warstwa 2 = legalizowana kontrabanda (F-14); brutalist łamie WCAG bez manifestu wyjątków (F-13). Fix: lint rozszerzony o warstwę 2 + jawny per-preset manifest wyjątków WCAG.

### D) JSON Schema v1

14. Rzemieślniczo solidne; wady: F-06 (forward-compat zepsuty u korzenia), F-19 (lengthValue), duplikacja definicji między schematami (brak współdzielonych `$defs`).
15. **31-value enum** = koordynacyjne wąskie gardło + legalizuje nonsens (`menu-full` na stronie SaaS przechodzi). Fix: pattern w schemacie + `blocks-registry.json` wersjonowany niezależnie + CI job w obu repo porównujący registry z `blocks/types.ts`.
16. **bilingualString** — niewystarczający: brak rejestru grzecznościowego (`contentMeta.register: ty|pan-pani|panstwo` — bez tego regenerate_section i edycje CMS gubią spójność), brak `uk` (1M+ ukraińskojęzycznych mieszkańców PL) i `de`, brak limitów długości per rola (hero title!).

### E) MCP server

17. Rdzeń dobry; braki: `list_clients` (15 linii kodu, brak #1), parametr `include` w get_design_state (blob 100KB+ w kontekst agenta).
18. Interface Tool 2 w 80% dobry (resolver locatora zostaje); wady: brak selektora wystąpień (`hero@2`), F-15, F-16.
19. Enum 9 kodów: dodać `SECTION_NOT_FOUND`/`PAGE_NOT_FOUND`/`NOT_IMPLEMENTED`/`DAEMON_UNAVAILABLE`; podpiąć ajv (F-16); naprawić F-17.

### F) Testing

20. Strategia 4-tier poprawna koncepcyjnie; Tier 1 obecnie ≈ zero wartości (existsSync-only, F-18, F-03).
21. Brakujące testy wg wartości: (1) golden-output e2e z MockProviderem, (2) walidacja templates (data-block-type ∈ enum, `{{key}}` ⊆ content-patterns), (3) automatyczny kontrast WCAG z tokens.css (wykryłby F-13), (4) cykl życia `.complete` (wykryłby F-05), (5) zgodność tokens.css ↔ tokens.example.json, (6) MCP stdio integration, (7) ścieżki Windows.

### G) Luki krytyczne

22. **Windows toolchain** — ryzyko WYSOKIE; stan gorszy niż opisany (zepsuty częściowy node_modules). 100% deklaracji "✅" Phase 5-7 niezweryfikowanych. Mitygacje: prebuilds better-sqlite3 / pin Node / WSL2 z jawną strategią `ROduQ_OUTPUT_DIR` (F-21).
23. Priorytety definicji-bez-implementacji: **P0** skill runtime + LLM layer + toolchain; **P1** UI briefu (F-20), ajv w write-path, regenerate_section; **P2** `od mcp`, cache/rate-limit/telemetry/health; **P3** Playwright, HMR, marketplace.
24. Minimalna ścieżka do v1.0: toolchain (0.5-1 d) → vertical slice CLI-driven `od roduq-generate` (3-5 d) → multi-variant = 3× slice (1-2 d) → pick+consume (1-2 d) → naprawy kontraktowe (1 d) → minimalny UI (3-5 d). **Razem 10-15 dni roboczych.** Szczegóły: [REMEDIATION_PLAN.md](REMEDIATION_PLAN.md).

## Werdykt końcowy

Fundament intelektualny (kontrakty, konwencje, polska specyfika głosów, taksonomia wariantów) — na poziomie dobrego zespołu produktowego. Główne ryzyko to nie Windows toolchain, lecz **kultura deklarowania zamiast weryfikowania**. Najbliższe 2 tygodnie powinny być nudne: install, build, run, fix — zero nowych dokumentów. Potem projekt ma realną szansę być czymś, czego Framer i Webflow nie skopiują.
